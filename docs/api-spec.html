1. 인증 / 온보딩

회원가입은 병원(관리자용 admin-web/server_admin)에서 등록한 환자번호(patientNo) + 이름 + 생년월일 + 전화번호가 전부 일치해야만 가능하다 v0.7 — 실제 시술 이력 없는 자유 가입은 막혀있다(별도 인증코드 발급 절차는 없음). 의료진(데스크)이 환자 방문 시 먼저 emr_patients에 환자 정보·시술 이력을 입력해두면, 환자가 그 환자번호 + 본인 이름 + 생년월일 + 전화번호로 신원을 증명하고 앱 계정을 만드는 순서다. 로그인은 이메일/비밀번호만 사용한다.

POST/auth/signup/pre-check 회원가입 1페이지 — 신원 사전 확인 v0.9

회원가입 화면을 2페이지로 나눌 때(1페이지: 환자번호+이름+생년월일+전화번호, 2페이지: 이메일+비밀번호+관심목표) 1페이지에서 계정을 만들지 않고 신원 일치 여부만 먼저 확인하는 용도. emr_patients 조회만 하고 아무것도 쓰지 않는다(부수효과 없음, claim 안 함).

v0.10 다른 클리닉의 미가입 형제 행 일괄 연결

AAC 산하 여러 클리닉(엠레드/더나/웜)을 다닌 고객이 아직 어느 클리닉에서도 회원가입 전이면, 클리닉마다 별도 emr_patients 행이 생겨 있는 상태다. 이 상태에서 그중 한 클리닉 환자번호로 회원가입하면, 이름+생년월일+전화번호가 일치하면서 아직 claimed_user_id가 없는 다른 클리닉의 행 전부를 같은 시점에 같은 계정으로 함께 claim한다(각 형제 행의 시술 이력·이용권도 전부 이 계정으로 이관됨) — 방문 순서·가입 순서와 무관하게, 결과적으로 한 사람은 하나의 앱 계정으로 합쳐진다. 형제 행이 없으면 이 단계는 아무 일도 하지 않는다. server_admin POST /patients의 "다중 클리닉 자동 연결"(이미 가입된 계정에 새로 등록하는 행을 즉시 연결하는 반대 방향 케이스, admin-api-spec.html 참고)과 짝을 이룬다.

v0.6 — 가상 EMR 기반 회원가입으로 전면 교체

실제 클리닉처럼 "환자가 앱에 가입하기 전에 의료진이 먼저 시술 이력을 입력해둔다"는 흐름을 반영해, 회원가입 방식을 이메일/비밀번호 자유 가입에서 환자번호+이름+생년월일 일치 기반 가입으로 교체했다.

  • 신규 관리자용 스택 — 관리자 웹(admin-web, 별도 GitHub 저장소)과 그 백엔드 server_admin/(포트 4100, server/와 동일 컨벤션)이 추가됨. 클리닉별 관리자 로그인(3계정)을 거쳐 환자 등록, 시술기록/이용권 입력을 수행한다. server_admin API는 이 문서(고객용 server/) 범위 밖 — docs/admin-api-spec.md 참고.
  • 신규 스테이징 테이블(server/db/migrations/006_add_admin_emr_staging_tables.sql) — emr_patients/emr_care_records/emr_memberships. auth.users와 완전히 무관하게 독립 존재하며 claim 전까지의 "미연결" 데이터를 보관한다. 상세 스키마는 db-schema.html 참고.
  • POST /auth/signup 시그니처 전면 교체 — {email,password,name,phone,birthDate} → {patientNo,name,birthDate,email,password,interestGoals}. 이름/생년월일은 자유 입력이 아니라 신원 확인용으로 emr_patients 원본과 대조되고, 전화번호는 요청에 아예 없이 원본에서 그대로 가져온다. 가입 성공 시 emr_care_records/emr_memberships가 실제 care_records/memberships로 1회성 이관되고, 실패 시 방금 만든 Auth 계정은 롤백(CASCADE로 하위 데이터 자동 정리)된다. (처음엔 인증코드 발급 방식으로 설계했다가 마이그레이션 010에서 이름+생년월일 대조 방식으로 대체 — signup_verification_codes 테이블은 제거됨)
  • PHONE_ALREADY_EXISTS 에러 제거 — 전화번호 중복 체크 자체가 사라짐(전화번호는 이제 EMR 원본에서 오는 값이라 애초에 클라이언트가 입력하지 않음). 대신 PATIENT_NOT_FOUND/PATIENT_ALREADY_CLAIMED/PATIENT_IDENTITY_MISMATCH 3종 신규 추가.

v0.7 — 회원가입 신원확인에 전화번호 추가

POST /auth/signup의 신원확인 항목을 patientNo+이름+생년월일 3종에서 patientNo+이름+생년월일+전화번호 4종으로 강화했다. 관리자 쪽 환자 등록(POST /patients)이 이름+생년월일+전화번호로 중복 판정을 하는 것과 대칭을 맞추고, 이름+생년월일만으로는 동명이인/오탈자 신원확인이 약하다는 문제를 보완하기 위함.

  • Request에 phone 필드 추가 — 관리자 쪽(server_admin/src/validators/patients.validators.ts)과 동일한 포맷(/^\d{9,11}$/, 하이픈 없는 숫자 9~11자리)으로 검증한다. server/src/validators/auth.validators.ts.
  • auth.service.ts의 signup() — emr_patients에서 조회한 patient.phone을 input.phone과 비교하는 조건이 이름/생년월일 비교에 추가됨 — 하나라도 다르면 기존과 동일하게 400 PATIENT_IDENTITY_MISMATCH.
  • profiles.phone에 채우는 값은 변함없이 EMR 원본(patient.phone)이다 — 클라이언트가 보낸 phone은 신원확인에만 쓰이고 저장값의 출처는 아니다(정상적으로 신원확인을 통과했다면 두 값은 어차피 동일).
  • 회원가입 화면(와이어프레임)에 전화번호 입력란 추가가 필요 — 클라이언트(앱) 쪽 변경사항은 이 문서(서버 스펙) 범위 밖.

v0.8 — 관리 추천을 실제 사업장 카탈로그 기반으로 교체

v0.9 — 회원가입 1단계 신원 사전 확인 API 추가

프론트가 회원가입 화면을 "환자번호+이름+생년월일+전화번호 확인" 1페이지와 "이메일+비밀번호+관심목표 입력" 2페이지로 분리하기로 결정 — 내용이 많아 한 화면에 다 넣기엔 복잡하다는 이유. 1페이지에서 신원이 틀렸는지를 바로 알려줘야 해서, 계정 생성 없이 신원 일치 여부만 확인하는 POST /auth/signup/pre-check를 신규 추가했다.

  • DB 변경 없음 — 신규 마이그레이션 불필요. emr_patients 조회만 하고 아무것도 쓰지 않는다(claim 안 함, 계정 생성 안 함).
  • 구현 — auth.service.ts의 signup() 안에 있던 신원확인 로직(환자번호로 조회 → claim 여부 → 이름/생년월일/전화번호 대조)을 checkPatientIdentity()로 분리해 signup()과 preCheckSignup() 둘 다 재사용한다 — 신원확인 규칙이 한 곳에만 존재해 pre-check와 실제 가입이 서로 다른 기준으로 판정될 여지가 없다.
  • 에러 코드는 POST /auth/signup과 완전히 동일(PATIENT_NOT_FOUND/PATIENT_ALREADY_CLAIMED/PATIENT_IDENTITY_MISMATCH) — 프론트가 두 단계에서 같은 에러 처리 로직을 재사용할 수 있도록 의도적으로 맞췄다.
  • 부수효과 없음을 라이브로 검증 — 실제 환자(EMR-P-A1C085)로 정상 일치(200)/전화번호 불일치(400)/존재하지 않는 환자번호(404) 3가지 경로를 확인 후, pre-check 호출 전후로 emr_patients.claimed_user_id가 계속 null인 것을 재조회로 확인(claim이 실제로 안 일어남).
  • 주의: pre-check를 통과했다고 2단계(실제 POST /auth/signup)가 반드시 성공하는 건 아니다 — 두 요청 사이에 다른 계정이 같은 환자번호로 먼저 가입하면(레이스 컨디션) 2단계에서 409 PATIENT_ALREADY_CLAIMED가 날 수 있다. 프론트는 2단계 실패도 여전히 처리해야 한다.

v0.10 — 사업장:회원 1:1 한계 해결 (다중 클리닉 자동 연결)

Slack에서 "AAC 산하 여러 클리닉을 다니는 고객이 두 번째 클리닉부터는 앱에 기록을 남길 수 없다"는 문제가 보고됐다. 원인 분석: emr_patients.brand로 환자 행을 클리닉별로 완전히 격리해둔 구조라, 같은 사람이 클리닉 A/B를 각각 방문하면 행이 두 개 생기는데 앱 계정(claim)은 그중 하나에만 걸 수 있었다 — 이미 A 번호로 가입한 사람이 B 번호로 다시 가입을 시도하면 profiles.phone unique 제약에 걸려(신원확인은 통과한 뒤) 일반화된 500 INTERNAL_ERROR로 실패했다. 결과적으로 두 번째로 방문한 클리닉은 이 고객의 시술기록을 영원히 스테이징 테이블(emr_care_records)에만 쌓을 수 있고 실제 앱에는 반영할 방법이 없었다.

DB 스키마 변경 없이 두 가지 방문 순서를 모두 커버하도록 해결:

  • 먼저 등록된 클리닉 → 나중 가입(이 문서 범위) — 여러 클리닉에 미가입 상태로 흩어져 있던 "같은 사람" 행이, 그중 한 클리닉 번호로 가입하는 순간 전부 같은 계정으로 한꺼번에 claim된다(위 "1. 인증/온보딩"의 "다른 클리닉의 미가입 형제 행 일괄 연결" 참고). auth.service.ts에 migrateEmrDataToApp()을 공용 함수로 뽑아, 본인 patientId뿐 아니라 형제 행 각각에도 동일하게 적용한다.
  • 이미 가입된 계정 → 다른 클리닉에 새로 등록(server_admin 쪽, admin-api-spec.md "다중 클리닉 자동 연결과 마스킹" 참고) — POST /patients가 새 환자 행을 만들 때 이름+생년월일+전화번호가 일치하는 다른 클리닉의 이미 claim된 행이 있으면, 그 계정으로 등록 즉시 자동 연결한다. 순수하게 server_admin 응답/로직 변경이라 이 문서 범위 밖이지만, 결과적으로 이 문서의 GET /home/summary/GET /care-records/GET /memberships 등에서 고객이 보는 데이터가 여러 클리닉 걸 다 포함하게 되는 원인이라 함께 남겨둔다.
  • 라이브 검증 완료 — 두 방문 순서 시나리오 모두 실제 회원가입 → 시술기록 추가 → GET /home/summary/GET /care-records로 고객 앱 화면에 다른 클리닉 기록까지 정상적으로 합쳐져 보이는지 end-to-end로 확인, 테스트 데이터는 전부 정리함.
  • 안내 발송(SMS 등)은 아직 미구현 — 다른 클리닉에서 자동 연결됐을 때 고객에게 알려주는 로직은 notifyExistingAccountLinked(server_admin) 스텁으로 로그만 남긴다. SMS 인프라가 비용 문제로 이미 한 번 제거된 바 있어(server/README.md 참고) 재도입 여부·수단은 미정.
  • claim 판별에 신규 컬럼을 쓰지 않음 — 자동 연결된 행은 created_at과 claimed_at을 INSERT 시점에 동일한 값으로 채워 "등록과 동시에 claim됨"을 구분한다. 이 구분은 server_admin 응답 마스킹에만 쓰이고, 고객용 server/ API 응답에는 영향 없음(claim된 계정 하나로 보이는 건 동일).
