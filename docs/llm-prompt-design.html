LLM 프롬프트 설계

LLM은 GET /aftercare/daily-guide, POST /aftercare/questions, GET /recommendations/next-care(v0.2 신규) 세 곳에서 호출된다. 카테고리 검증과 위험 신호 감지는 LLM 호출 전 규칙 기반으로 처리해, LLM은 "이미 안전하다고 확인된 요청"만 받는다. 추천의 "어떤 시술을 고를지" 자체도 여전히 규칙 기반 — LLM은 문구 생성만 담당한다.

v0.2 3개 호출 지점 OpenAI 전환 구조화 출력 강제
목차
공통 원칙 파이프라인 1. 일차별 가이드 2. 챗봇 Q&A 3. 다음 관리 추천 버전 관리 미확정 사항

공통 원칙

  • 1근거는 오직 두 가지 — 검수된 관리 가이드(RAG 소스)와 환자 컨텍스트(관리 이력·경과일·알러지·의사 코멘트). 이 밖의 지식으로 답하지 않는다.
  • 2의료적 진단·처방 금지 — 질환명 진단, 회복 완료 판정, 약물 처방, 응급 상태 단독 판단을 생성하지 않는다.
  • 3위험 신호·범위 밖 카테고리는 LLM에 도달하기 전에 규칙 엔진이 먼저 걸러낸다.
  • 4구조화된 출력 강제 — 두 엔드포인트 모두 고정 JSON 스키마로만 응답받는다(모델의 JSON 모드/함수 호출 사용).
  • 5알러지·의사 코멘트는 항상 컨텍스트에 포함 — medical_data_access_log에 accessed_by: 'llm_system'으로 접근 기록.

파이프라인 두 엔드포인트 공통

규칙 필터 → 컨텍스트 조립 → LLM 호출 → 출력 검증 → 저장/응답, 다섯 단계는 두 엔드포인트가 동일하게 따른다.

1. GET /aftercare/daily-guide 하루 1회 캐시

캐시 미스일 때만 호출된다(care_record_id + 오늘 날짜 조합이 aftercare_guides에 없을 때). elapsed_range(예: "3-7")는 LLM이 정하는 게 아니라 규칙(구간 lookup)으로 먼저 결정 — LLM은 그 구간의 검수된 가이드를 환자 상황에 맞게 자연어로 풀어 쓰는 역할만 한다.

컨텍스트 주입 필드
필드출처용도
care_name / care_date / days_elapsedcare_records언제 무슨 시술을 받았는지
part_of_body / brandcare_records시술 부위(배열, 중복 선택 가능) 맥락
doctor_commentcare_records해당 시술 건 의사 코멘트
allergies / chronic_conditionsmedical_profiles특정 성분·행동 회피 근거
doctor_general_commentmedical_profiles환자 전반 의사 코멘트
검수된 가이드 원문내부 레퍼런스 문서답변의 유일한 사실 근거

아래 "검수된 가이드"와 "환자 정보"만을 근거로, 해당 환자의 경과일에 맞는
사후관리 주의사항을 안내하세요.

규칙:
- 검수된 가이드에 없는 내용을 지어내지 마세요.
- 질환을 진단하거나, 회복 완료를 판정하거나, 약물을 처방하지 마세요.
- 환자의 알러지/기저질환에 해당하는 성분·행동이 검수된 가이드에 포함되어
  있다면, 반드시 회피 항목으로 강조하세요.
- 반드시 아래 JSON 스키마로만 응답하세요. 다른 텍스트를 추가하지 마세요.
출력 스키마
{
  "mustAvoid": ["string"],
  "basicCare": ["string"],
  "nextCheckDate": "YYYY-MM-DD | null"
}

→ aftercare_guides.must_avoid / basic_care / next_check_date에 저장, generated_by='llm'

503 GUIDE_GENERATION_FAILED → 검수된 가이드 원문 그대로 폴백

2. POST /aftercare/questions 매 요청 호출

질문이 매번 다르므로 캐싱 없음.

사전 규칙 필터
조건처리
category가 지원 6종 밖 (세안·샤워/화장·렌즈/운동·사우나/음주·흡연/화장품·성분/증상)422 UNSUPPORTED_CATEGORY, LLM 미호출
위험 신호 키워드 포함 (통증 증가, 출혈, 시야 이상, 고열, 호흡곤란 등)status: expert_required, LLM 미호출
System Prompt (초안)
당신은 AAC 웰니스 클리닉의 사후관리 Q&A 도우미입니다.
아래 카테고리 범위 안에서만 답변하세요: 세안·샤워, 화장·렌즈, 운동·사우나,
음주·흡연, 화장품·성분, 증상.

규칙:
- 답변은 "검수된 가이드"와 "환자 정보"에서만 근거를 찾으세요.
- 근거가 부족하거나 이 서비스 범위를 벗어난 질문이면 status를
  "out_of_scope"로 반환하고 answer는 비워두세요.
- 질환 진단, 회복 완료 판정, 약물 처방에 해당하는 답을 만들지 마세요.
- 환자의 알러지/기저질환과 관련된 질문이면 반드시 그 정보를 반영해 답하세요.
- 반드시 아래 JSON 스키마로만 응답하세요.
출력 스키마
{
  "status": "answered | out_of_scope",
  "answer": "string | null"
}

expert_required는 이미 규칙 단계에서 결정되어 LLM에 도달하지 않는다 — LLM은 answered/out_of_scope 둘 중 하나만 선택. 서버가 answeredBy: "llm", basedOn을 붙여 최종 반환

503 ANSWER_GENERATION_FAILED → 재시도 안내 문구 반환 (질문마다 달라 고정 폴백 어려움)

3. GET /recommendations/next-care(및 상세) v0.2 신규 · 2026-08-18

daily-guide/questions와 달리 "무엇을 답할지" 자체는 규칙 기반이 그대로 정한다(관심 목표·최근 시술과 procedures.category_tags 매칭 점수). LLM은 이미 정해진 시술 1개에 대해 "왜 추천하는지" 자연어 문구만 생성한다 — 잘못된 시술을 추천할 위험은 LLM과 무관하다. reasons는 호출마다(/next-care, 상세, /home/summary) 매번 생성되고, detailDescription은 상세 조회에서 카탈로그에 실제 설명이 없을 때만 추가 호출된다.

컨텍스트 주입 필드
필드출처용도
추천 시술명 / 설명 / categoryTagsproceduresLLM이 언급할 수 있는 유일한 "사실"
interestGoals / 겹치는 태그profiles.interest_goals왜 이 고객에게 맞는지 연결고리
최근 관리명care_records최근 이력과의 연관성 언급
System Prompt (recommendation.prompt.ts)
당신은 AAC 웰니스 클리닉의 다음 관리 추천 도우미입니다.
아래 "추천된 시술 정보"와 "고객 정보"만을 근거로, 이 시술이 왜 추천되는지 자연스러운 한국어
문장으로 설명하세요.

규칙:
- 주어진 정보에 없는 효능·효과를 지어내지 마세요.
- 의료적 진단이나 시술 효과를 보장하는 표현은 쓰지 마세요.
- 관심 목표 또는 최근 관리와 겹치는 부분이 있으면 그 연결고리를 구체적으로 언급하세요.
- 반드시 도구 호출(tool call)로만 응답하세요.
출력 스키마
{
  "reasons": ["string"],
  "detailDescription": "string"
}
503 없음 — 1회 재시도 후에도 실패하거나 OPENAI_API_KEY 미설정 시 정적 템플릿 문구로 조용히 폴백(추천 자체는 계속 뜸)

버전 관리 추후 확장

현재 generated_by / answered_by는 'llm' 고정값이다. 프롬프트나 모델을 바꿔가며 실험하게 되면 prompt_version, model_name 컬럼을 aftercare_guides/questions에 추가해 어떤 버전이 어떤 답을 냈는지 추적할 수 있게 확장한다 (지금은 MVP 범위 밖).

미확정 사항 기획/전문가 검토 필요

  • 실제 사용할 LLM 모델 선택
  • 검수된 관리 가이드(RAG 소스) 문서를 어떤 형식·어디에 저장할지 (DB 테이블 vs 정적 파일) — 아직 스키마에 없음
  • 위험 신호 키워드 목록의 구체적 범위 (전문가 검수 필요)
  • 출력 검증(금지어 필터) 실패 시 재시도 vs 즉시 폴백 정책
  • reference_guides의 care_type 7종 중 5종(energy_lifting/botox/filler/skin_booster/hair_removal)이 미검수 스텁 설계 원칙 위반 — 위 "검수된 가이드만 근거로 삼는다" 원칙과 달리, reviewed_by/reviewed_at 컬럼을 코드가 검사하지 않아 미검수 문구도 peeling/laser_toning과 동일하게 LLM에 근거로 주입됨(2026-08-17 발견, server/README.md TODO 참고)
