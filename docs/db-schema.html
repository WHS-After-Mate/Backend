인증 (Supabase 관리) 직접 구현 안 함

이메일/비밀번호 계정, 비밀번호 해싱, access/refresh 토큰 발급·재발급·폐기는 전부 Supabase Auth가 처리한다. 우리 스키마는 auth.users.id를 FK로 참조만 한다. 전화번호 SMS 인증은 국내 업체 연동 비용 때문에 MVP 범위 밖으로 확정되어 제거됐다(004_remove_phone_verification.sql) — phone은 이제 조회·표시용 연락처 값일 뿐이다.

가입 흐름 v0.6 · 환자번호+이름+생년월일 대조 기반: POST /auth/signup({patientNo, name, birthDate, email, password, interestGoals}) → emr_patients에서 patient_no로 조회(없으면 PATIENT_NOT_FOUND, 이미 claimed_user_id 있으면 PATIENT_ALREADY_CLAIMED) → 조회된 name/birth_date가 요청값과 정확히 일치하는지 대조(불일치 시 PATIENT_IDENTITY_MISMATCH, 별도 인증코드 발급 없음) → supabase.auth.admin.createUser() → 생성된 user.id로 profiles insert + medical_profiles insert(emr_patients.notes를 doctor_general_comment로 이관) + emr_care_records/emr_memberships를 care_records/memberships로 1회성 이관(claim) + emr_patients.claimed_user_id/claimed_at 기록. 실패 시 Auth 유저 롤백(하위 테이블은 CASCADE로 자동 정리, emr_patients는 claim 전이라 그대로 남아 재시도 가능). v0.4 시점엔 signup_verification_codes로 발급하는 별도 인증코드 대조 방식이었으나 v0.6(010)에서 이 방식으로 대체되며 테이블 자체가 삭제됐다.
비밀번호 재설정/변경 구현 완료: 별도 테이블이 필요 없다. POST /auth/password/reset-request는 supabaseAnon.auth.resetPasswordForEmail()에 위임. reset-confirm은 {email, code, newPassword}를 받아 code를 supabaseAnon.auth.verifyOtp({ email, token: code, type: "recovery" })로 검증한 뒤 supabaseAdmin.auth.admin.updateUserById()로 처리한다(auth.service.ts) — Supabase 이메일 템플릿의 {{ .Token }} 숫자 코드를 그대로 쓰는 방식으로, 링크(access_token) 기반이었던 이전 설계에서 전환됐다. POST /profile/password(로그인 상태 변경)는 동일하게 updateUserById()로 처리(profile.service.ts) — 셋 다 Supabase Auth가 해싱/토큰을 전담하므로 테이블 추가 없음.

클리닉 EMR 연동 구조적 전제

이 서비스는 클리닉(AAC)의 의료 데이터베이스(EMR)에 이미 존재하는 환자 기록을 바탕으로 환자 본인에게 사후관리를 제공한다 — 환자가 자기 진료기록을 열람하는 patient-portal과 같은 구조다. care_records의 시술 이력, 알러지 정보, 의사 코멘트는 우리 앱이 만드는 원본 데이터가 아니라 클리닉 EMR에서 동기화(sync)해온 사본이다.

원본(source of truth)은 클리닉 EMR(별도 시스템, 이 저장소 범위 밖)이고, 우리 DB는 필요한 필드만 읽기 전용으로 동기화해 patient-facing 앱과 LLM 컨텍스트에 쓴다. MVP는 실제 클리닉 EMR 시스템 연동 대신, 관리자용 가상 EMR 스테이징 테이블(emr_patients 등, 아래 "가상 EMR 스테이징 테이블(006)" 절)에 의료진이 직접 입력한 데이터를 회원가입 시 1회성으로 이관(claim)한다. external_*_id / synced_at / source_system 필드는 나중에 실제 배치 동기화(ETL)로 교체할 수 있도록 미리 넣어둔 것이다. 알러지·의사 코멘트는 GET /aftercare/daily-guide, POST /aftercare/questions의 LLM 컨텍스트에 반드시 포함해 "알러지 있는 성분을 권하는" 실수를 막는다. (데모용 시드 스크립트 seed.ts는 이 claim 흐름과 무관하게 별도로 계정을 직접 생성한다.)

설계 결정

추천(Recommendation)은 테이블 없음

규칙 기반이라 매 요청 시 care_records+memberships+profiles.interest_goals로 즉석 계산. recommendationId는 응답 시점에 생성해 상세조회 라우팅에만 쓴다.

refresh token 테이블 없음

Supabase Auth가 내부적으로 관리. POST /auth/refresh·/logout은 Supabase SDK 호출로 대체.

알림 설정은 미구현으로 제거

실제로 읽어 분기하는 발송 로직이 없는 placeholder였음(발송 스케줄러 미구현). GET/PATCH /notifications/settings 엔드포인트와 4개 컬럼 전부 삭제(005_remove_notification_settings.sql).

캘린더는 집계 쿼리

care_records를 월 단위로 GROUP BY care_date. 별도 마커 테이블 유지 비용 없음.

1일 1회 LLM 생성은 DB 제약으로

aftercare_guides의 (care_record_id, generated_date) UNIQUE로 중복 생성을 애플리케이션 로직이 아니라 DB가 막는다.

전화 인증은 미구현으로 제거

국내 SMS 업체 연동 비용이 MVP 범위 밖이라 판단, phone_verifications 테이블·phoneVerifiedToken 흐름 전부 삭제(004_remove_phone_verification.sql).

알러지·의사코멘트는 별도 테이블

medical_profiles로 profiles와 분리 — EMR 동기화 대상이라 접근 권한·감사 로그를 다르게 관리.

의료정보 접근은 감사 로그 필수

medical_data_access_log로 알러지·의사 코멘트를 "누가/언제/왜" 봤는지 기록 (LLM 참조 포함).

실서비스 전환 시 법적 검토 필요

클리닉 EMR과의 실제 연동은 개인정보 제3자 제공/위탁 동의, 의료법 관련 규정 검토가 필요. MVP는 가상 데이터 시드로 우회.

추천 상세 확장 필드 전용 테이블 없음 v0.3 · 구현 완료

relatedRecentCares/categoryTags(v0.15, 구 popularWithSimilarCustomers)/clinicContacts는 care_records 조회·추천 시술의 procedures.category_tags 그대로 노출·businesses 조회로 즉석 계산 — 추천 테이블 없음과 같은 이유.

비밀번호 재설정/변경 전용 테이블 없음 v0.3 · 구현 완료

Supabase Auth가 재설정 토큰 발급·검증·해싱을 전담. 전화 인증과 달리 국내 제약이 없어 자체 구현 불필요.

가상 EMR 스테이징은 auth.users와 완전 분리 v0.4 · 구현 완료

emr_patients 등은 server_admin이 다루는 "계정 연결 전" 데이터라 고객용 테이블과 독립적으로 존재. claim(회원가입) 시점에만 1회성 복사되며, 이후 EMR 테이블에 추가된 데이터는 자동 반영되지 않는다(의도적 범위 제한).

관리자 로그인은 Supabase Auth가 아니라 자체 bcrypt+JWT v0.6 · 008

클리닉 계정 3개가 고정이라 가입 플로우 자체가 필요 없고(시드로만 생성), 고객용 auth.users와 완전히 다른 성격의 인증(브랜드별 격리)이라 별도 테이블+토큰 체계로 분리하는 편이 단순함.

관리자용 신규 스택: 관리자 웹(admin-web, 별도 GitHub 저장소)과 그 백엔드 server_admin/(포트 4100, server/와 동일 컨벤션)이 이 마이그레이션과 함께 추가됐다. server_admin은 이 테이블들만 다루고 server/의 기존 고객용 테이블은 건드리지 않는다. 이 마이그레이션은 이미 Supabase 프로젝트에 적용됐다. (이 시점엔 "로그인 없이 항상 열림"이 데모 범위 결정이었으나, v0.6(008)에서 클리닉별 로그인이 추가되며 뒤집혔다 — 아래 절 참고.)

치료-부위 카탈로그 추가 013

server/db/migrations/013_add_treatment_catalog.sql — 관리자 웹 프로토타입(docs/WHS_After_Mate_Admin_revised.html)의 "치료명 고르면 관리 부위 자동 채움" 방식을 도입하기 위해 public.treatment_catalog 신규 추가(위 테이블 정의 참고). 스키마 변경과 함께 server_admin의 이용권 처리 로직도 두 가지 바뀌었다:

  • 이용권 만료일 실제 적용 — memberships/emr_memberships의 expires_at 컬럼은 001부터 있었지만 그동안 server_admin이 값을 넣지 않아 항상 null이었다. 이제 새 이용권을 만들 때 그 시술 날짜(careDate) 기준 +1년으로 계산해 채우고, 차감 시 만료 여부를 확인해 만료됐으면 409 MEMBERSHIP_EXPIRED로 거부한다(DB 스키마 변경 없음, 애플리케이션 로직만 추가)
  • 이용권 자동 이어쓰기 — POST .../care-records에 totalSessions(직접입력)로 요청하면, 같은 product_name+같은 total_count로 아직 유효한(소진·만료 안 된) 이용권이 있는지 먼저 찾아서 있으면 새로 만들지 않고 그 이용권에 이어서 차감한다(관리자 프로토타입의 "패키지 자동 이어쓰기" 동작 재현)

자세한 API 계약은 docs/admin-api-spec.md v0.3 참고.

실제 사업장/시술 카탈로그 추가 015

server/db/migrations/015_add_care_catalog.sql — 사용자가 실제 사업장 데이터(docs/care_procedure_template.xlsx — 엠레드/더나/윔 3곳, 실시술 46종 + concernTag 매칭, docs/care_recommendation_data_guide.md에 설계 문서)를 전달하면서, 다음 관리 추천(recommendations.service.ts) 로직이 실데이터를 전혀 참조하지 않던 문제가 드러나 신규 테이블 public.businesses/public.procedures를 추가하고(위 테이블 정의 참고) 추천 알고리즘을 전면 교체했다.

  • concernTag 고정 10종은 server/src/lib/concernTags.ts에 상수로 관리(DB 테이블 아님) — 앱의 관심목표 칩과 동일한 값이어야 매칭됨

  • 실계정으로 라이브 검증 완료 — 자세한 API 계약 변경은 docs/api-spec.md v0.8 참고
