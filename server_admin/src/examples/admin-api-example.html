WHS After Mate — admin-web이 호출하는 Admin API 실험용 예시 페이지

이 파일은 실제 admin-web(별도 저장소) 프론트가 아니다 — server_admin API를 fetch()로 직접 눌러보기 위한 임시 테스트 페이지일 뿐이다. 서버 코드를 import하지 않고 오직 HTTP 요청만 보낸다. 먼저 다른 터미널에서 server_admin을 npm run dev로 켜둔 상태여야 한다(기본 포트 4100). E 단계(가입 연동 테스트)를 실행하려면 server(포트 4000)도 함께 켜져 있어야 한다.

0. 관리자 로그인 — POST /auth/login

아래 A~E는 이제 전부 로그인 토큰이 있어야 호출된다. 클리닉 3곳 중 하나로 로그인하면 이후 요청에 Authorization: Bearer <token>이 자동으로 실린다. 테스트 계정(npm run seed:admins로 생성): amred/amred1234, derna/derna1234, wim/wim1234. 

(아직 로그인 안 함)

현재 로그인 클리닉: (로그인 필요)

A. 환자 등록 — POST /patients

실제 클리닉 데스크에서 환자가 처음 방문했을 때 입력하는 정보. 성공하면 서버가 환자번호(patientNo)만 발급한다(인증코드는 없음 — 회원가입은 이 patientNo+이름+생년월일 일치로 신원확인). 여기서 등록한 환자의 id는 아래 "현재 대상 환자"(C~E 단계용), patientNo·이름·생년월일은 E 단계(회원가입 연동 테스트)의 입력칸에 각각 자동으로 채워진다.

이름+생년월일+전화번호가 전부 같은 환자가 이 클리닉에 이미 있으면 새로 만들지 않고 그 환자를 그대로 재사용한다 — 에러가 아니라 200 + duplicate: true로 응답한다(201이면 새로 만든 것, 200+duplicate면 기존 환자였다는 뜻). 이때 기타사항이 바뀌었으면 그 값으로 갱신까지 해준다. 전화번호칸은 버튼 누를 때마다 자동으로 새로 채워지므로 평소엔 새 환자로 등록되는데, 아래 이름·생년월일·전화번호를 방금 등록한 값과 똑같이 맞추고(기타사항은 다르게 바꿔서) 다시 누르면 이 동작을 직접 볼 수 있다. 

(아직 실행 안 함)

현재 대상 환자 (아래 C~E 단계가 전부 이 값을 사용)

A에서 환자를 등록하면 자동으로 채워진다. 이미 등록해둔 다른 환자를 대상으로 C~E를 테스트하고 싶으면 B(환자 목록 조회) 응답의 id 필드 값을 여기 직접 붙여넣으면 된다 — patient_no(EMR-P-XXXXXX 형태의 환자번호)가 아니라 UUID 형태의 id다. patient_no는 아래 E 단계(실제 회원가입 연동 테스트)에서 따로 쓴다.

B. 환자 목록/검색 — GET /patients?search=

로그인하면 자동으로 전체 목록을 불러온다. 검색어를 입력하면 버튼 없이 실시간(입력 300ms 후)으로 다시 조회해서 목록이 그때그때 바뀐다. 이름·전화번호·환자번호 부분일치 검색, 비워두면 전체 목록. 목록이 길어지면 아래 박스 안에서만 스크롤된다.

(로그인하면 자동으로 채워짐)

C. 환자 상세 조회 — GET /patients/:patientId

프로필 + 시술기록 + 이용권을 한 번에 반환한다. 위 "현재 대상 환자" 칸의 patientId를 사용한다.

(아직 실행 안 함)

D. 시술 기록 추가 — POST /patients/:patientId/care-records

위 "현재 대상 환자"의 patientId를 대상으로 추가한다. 이용권 추가 API는 따로 없다 — 시술과 이용권은 항상 1:1이라, 아래 라디오로 ① 이미 갖고 있는 이용권에서 1회 차감하거나 ② 직접 입력으로 새 이용권을 만들면서 1회차를 바로 소비하는 것 중 하나만 고른다(실제 admin-web 화면은 라디오 버튼 UI지만, 이 테스트 페이지는 같은 의미를 select로 단순화했다). careType은 /aftercare/daily-guide가 검수 가이드를 찾는 매칭 키다. 현재 시드 데이터는 peeling/laser_toning 2종만 지원하므로, 나중에 이 환자로 가입해 daily-guide까지 테스트해보려면 둘 중 하나를 써야 한다. 이 환자가 이미 회원가입(claim)한 상태여도 추가할 수 있다 — 그 경우 emr_care_records가 아니라 실제 care_records/memberships에 바로 기록된다(응답의 source 필드로 "emr"/"app" 어느 쪽인지 확인 가능).

brand는 더 이상 여기서 입력하지 않는다 — 위에서 로그인한 클리닉으로 자동 기록된다.

(아직 실행 안 함)

이용권도 함께 정리된다 — 방금 직접입력으로 새로 만든 이용권이었으면 통째로 삭제되고, 기존 이용권에서 차감한 거였으면 그 차감만 1 되돌아간다(이용권을 따로 지우는 API는 없음). 

(아직 실행 안 함)

E. (연동 테스트) patientNo+이름+생년월일로 실제 회원가입 — POST /auth/signup (server, 포트 4000)

여기부터는 server_admin이 아니라 고객용 server를 호출한다. 인증코드는 없다 — patientNo+이름+생년월일이 위 A에서 등록한 값과 정확히 일치해야 가입이 진행된다. 성공하면 실제 앱 계정이 생성되고, 시술기록/이용권이 care_records/memberships로 1회성 이관(claim)되는지까지 전체 흐름을 확인할 수 있다. 성공 후 같은 환자번호로 다시 이 버튼을 누르면 409 PATIENT_ALREADY_CLAIMED가 나는 것도, 이름/생년월일을 일부러 틀리게 바꾸면 400 PATIENT_IDENTITY_MISMATCH가 나는 것도 확인해볼 수 있다. 

(아직 실행 안 함)

F. 방문 고객수 — GET /visit-stats

오늘/어제/이틀 전, 로그인한 클리닉에 방문(시술기록이 있는)한 고객 수(중복 제거). 회원가입 전 고객(emr_care_records)과 회원가입 후 고객(care_records)을 합쳐서 센다. 

(아직 실행 안 함)

G. 예약 목록/취소 — GET /reservations?date= + DELETE /care-records/:careRecordId

F(visit-stats)는 날짜별 건수만 알려준다 — "누구를 취소할지" 고르려면 개별 항목이 필요한데, 그게 이 GET /reservations다. 날짜를 비우면 오늘(KST) 기준으로 조회한다. 각 행의 "취소" 버튼은 별도 "취소" API가 아니라 위 D에서 쓴 것과 똑같은 DELETE /care-records/:careRecordId를 그 행의 careRecordId로 호출할 뿐이다 (이용권 환불도 그 로직 그대로 적용됨) — 취소 후 목록이 자동으로 다시 조회된다.

(아직 실행 안 함)
